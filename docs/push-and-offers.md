# Push notifications and the care-request offer (card, native ring)

Push notifications, the Android notification card with Accept / Decline, and the native ring (own sound, card over other apps and the lock screen) for an instant care request.

> How the three parts fit: the native ring below handles an INSTANT request first (`showOfferNotification` calls it before anything else); the notification card in the middle section is its fallback and the card for scheduled visits. Where the card section lists a full-screen ring over the lock screen as not built, the native ring section supersedes it (`OfferActivity` shows over the lock screen).

## Push notifications

**Push notifications** (`services/pushNotificationService.ts`). A push for news that is also a row in the notification list carries `notification_id`, `redirect_type`, `redirect_id` (backend `app/core/notify.py`): a tap on the phone's notification, or on the notification the app posts itself when the push arrives while the app is open (Android draws a push itself only when the app is closed or in the background, so `expo-notifications` posts the same notification on the same `updates` channel: a banner with sound and an entry in the shade; not posted when that appointment or the Notifications list is already open; if posting fails, the in-app banner `components/common/feedback/NotificationToast`, the `notification` type of `config/toastConfig.tsx`, is shown instead), goes through `features/notification/openNotificationTarget.ts` (the same routing as a tap on a row in `NotificationPage`), marks the notification read and refreshes the bell and the list (`services/notificationEvents.ts`: `AppHeader` and `NotificationPage` listen). Care-request offers are still ignored in the foreground (the dispatch socket delivers them). Appointment news (confirmed, changed, cancelled, delayed, reminders) was the first user; the home-care notices are the second: a PATIENT is told each step of a visit (provider assigned / cancelled, on the way, arrived, started, an update, completed, no provider found: `redirect_type` `ancillary_scheduled` / `ancillary_booking`, so a tap opens the booking) and a PROVIDER is told when a patient cancels a visit they had accepted (`redirect_type` `provider_today`, a tap opens the Home tab, their Today screen; the text names no patient) and what the admin decided about their verification (a row under "Updates", no screen). `handleOpened` opens the screen from the push's `redirect_type` first (and marks the row read), and only for an older push that has none falls back to the booking id (`PATIENT_HOME_CARE_NEWS`). **System notifications (Android)**: a push shows as a banner with sound only if its channel was created with HIGH importance, and the app creates them natively at start-up: `plugins/withNotificationChannels.js` (listed in `app.json` `plugins`; run `npx expo prebuild --platform android` once so the existing `android/` folder gets it, then `npx expo run:android`) (`expo-notifications` is a dependency but has no entry in `app.json` `plugins`: its own Firebase service has a lower priority than `@react-native-firebase/messaging`'s, so Firebase messages still go to Firebase; the plugin only sets the icon/colour meta-data it reads) adds the channels `updates` and `care_requests` and `care_request_ring` (the ids the backend sends, `health_care_backend/app/core/push.py`; `care_request_ring` is the channel an INSTANT care request rings in: the phone's default ringtone as a ringtone, so it follows the ring volume, a repeating buzz, public on the lock screen. The app tells the server it has it when it registers its token, `pushNotificationService.ts::hasRingChannel` -> `ring_channel`, because an older build has no such channel and a push to it would land quietly. The plugin's second marker `withNotificationChannels.ring` means an `android/` folder prebuilt earlier still gets the channel on the next `npx expo prebuild --platform android`; and with the app open the offer sheet buzzes, `ProviderTodayContent.OFFER_VIBRATION`), FCM's default channel / small icon / colour (`assets/notification/notification-icon-<density>.png`, a white mark on transparent made from the app logo; `#2B6F71`) and copies the icons into `res/drawable-*`. A channel's importance is fixed once a phone has created it: a new purpose needs a new id. The plugin was checked with a prebuild in a throwaway copy (SDK 57 template, run twice: nothing duplicated). Token registration uses the full addresses in `API_ENDPOINTS.AUTH` (`SESSION_FCM_TOKEN`, `SESSION_NOTIFICATION_PROMPT`): a bare `/api/...` path has no server and fails on the phone with "No internet connection". Not run on a device yet: `npx tsc --noEmit` only.

## Care request card with Accept / Decline

**Care request card with Accept / Decline** (`services/offerNotification.ts`, Android; library `react-native-notify-kit`, the maintained fork of Notifee, which was archived in April 2026; it needs the New Architecture, which this app uses, and a NATIVE REBUILD after `npm install`). A system-drawn push cannot have buttons, so the backend sends a new care request as a DATA-ONLY high-priority push (`type` `NEW_CARE_REQUEST_OFFER` with `title`, `body` (lines separated by newlines), `channelId`, `requestId`, `visitPublicId`, `bookingType`, `expiresAtMs`) to a session that declared `offer_actions` (`pushNotificationService.sendToken`: `canDrawOffers()` = Android, the library's native module is linked and the `care_request_ring` channel exists; so an older native build or a dev server on one never claims it and gets the ordinary notification). The Firebase background handler (`registerBackgroundPushHandler`, set in `index.ts` at module load, so it runs with the app closed) calls `showOfferNotification`, which draws the card: title, the service and distance collapsed and one line per row expanded (Inbox style: a BigText paragraph ran the lines together on Samsung), a countdown in its header for an instant request (`showChronometer` / `chronometerDirection: 'down'` to `expiresAtMs`), `timeoutAfter` so it removes itself when the offer ends, `loopSound` so an instant request rings (the channel's default ringtone) until answered or ended, and the buttons **Decline** and **Accept** (`pressAction` without `launchActivity`, so a press does not open the app and works from the lock screen). A press arrives as `ACTION_PRESS` in `handleOfferEvent` (`notifee.onBackgroundEvent`, registered in `index.ts`; `onForegroundEvent` through `subscribeToOfferEvents` while the app is open): Accept stops the ring at once, calls `acceptCareRequestBackend` and shows a quiet result notification (channel `care_request_result`, created at runtime: "Request accepted, tap to open your visit" / "Taken by another provider" / "Couldn't accept the request"); Decline calls `rejectOffer`. A tap on the card (or its result) opens the app on the Home tab. The in-app offer sheet and a withdrawn offer remove the card (`dismissOfferNotification`). In the foreground nothing is drawn (the dispatch socket shows the sheet). Not built: a push to remove the card when ANOTHER provider accepts (it removes itself at the end of the offer, and a late Accept answers "Taken by another provider"), a full-screen ring over the lock screen (Android 14 limits the permission to calling and alarm apps), iOS. Not run on a device yet: `npx tsc --noEmit` only; test with the backend's `scripts/send_test_offer.py`.

## Native ring for an INSTANT request

**Native ring for an INSTANT request (ride-request style; Android)** (`plugins/offer-overlay/*.kt`, copied into `android/app/src/main/java/com/karolahealth/app/offer/` and declared / registered by `plugins/withOfferOverlay.js`, listed in `app.json` `plugins`; **native Kotlin lives in `plugins/offer-overlay/` and is copied into `android/` by the config plugin at prebuild; edit it there, then run `npx expo prebuild --platform android` (never `--clean`) and `npx expo run:android`**). The notification card above was not enough: a notification's sound and look are decided by Android / Samsung (channel settings, "Brief" pop-up, the cool-down on repeated alerts), so an instant request is now handled by our own foreground service. `showOfferNotification` calls `NativeModules.OfferOverlay.show` first (falls back to the notify-kit card when the module is missing or Android refuses the service). `OfferRingService` (foreground service, type specialUse) plays our own ring sound itself in a loop (`assets/sounds/new_request.wav`, a synthesised double bell "ding-ding", 2.4 s, copied to `res/raw/new_request` by the plugin; regenerate or replace the file and prebuild again; the phone's default ringtone is the fallback when the file is missing or cannot play) with `MediaPlayer` and `USAGE_NOTIFICATION_RINGTONE` (follows ring volume and the silent switch like a call), vibrates, and shows `OfferCard` (built in code: icon tile, "New visit request" + INSTANT tag, service, the server's lines, "Collect ₹..", countdown bar, Decline / Accept): **screen on + "Display over other apps" allowed** -> a window over whatever is on screen; **screen off or locked** -> a full-screen notification opens `OfferActivity` (shows over the lock screen, turns the screen on); **no permission** -> a heads-up notification with Decline / Accept buttons (channels `care_request_live_alert` / `care_request_live_quiet`, silent: the service rings). It ends at `expiresAtMs` (30 s), on an answer or when the in-app sheet answers (`dismissOfferNotification` -> `hide`). Accept / Decline start `OfferActionService` (a `HeadlessJsTaskService`), which runs the JS task `OfferAction` (`registerOfferHeadlessTask` in `index.ts`) -> `answerOfferFromNative` -> the same accept / reject APIs and result notification as above, so it answers with the app closed. The Today screen shows a prompt (`useOverlayPermission`, `AppInfoBanner`) until "Display over other apps" is allowed (`openOverlaySettings`). Needs a NATIVE REBUILD; scheduled visits keep the single notification card. Built and tried on a Samsung phone (ring, the card over other apps and over the lock screen, Accept / Decline with the app closed). Not built: removing the card when ANOTHER provider accepts, the extra lines of the mock ("1 visit · 15-20 mins · reach by", which the server does not send yet), iOS.
