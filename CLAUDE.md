# health_care_mobile/ — Mobile App (React Native + Expo)

Part of the [healthcare2](../CLAUDE.md) monorepo. See root CLAUDE.md for cross-service context. App name: "KarolaHealth" (`app.json` slug `karola-health`, Android package `com.karolahealth.app`, registered in Firebase project `karolahealth` via `google-services.json`). Has its own `.git` repo, separate from the rest of `healthcare2`.

## Stack

- React Native 0.86 on Expo SDK 57, React 19.2, TypeScript ~6.0 (strict mode)
- Navigation: React Navigation v7 (native-stack + bottom-tabs)
- UI: React Native Paper v5 (`PaperProvider`)
- HTTP: axios (custom instance with interceptors)
- Validation: Zod (`src/validation/authSchemas.ts`)
- Storage: `secureStorage.ts` wraps `expo-secure-store` for tokens (`access_token`/`refresh_token`); `@react-native-async-storage/async-storage` used for non-sensitive data. Network: `@react-native-community/netinfo` (backs `NetworkContext`/`OfflineBanner`)
- Native/Expo modules: camera, location, audio, video, speech-recognition, image-picker, file-system, device, screen-capture, maps, webview, signature-canvas, svg (+ svg-transformer), reanimated v4
- Firebase: `@react-native-firebase/app` + `messaging` (push notifications), `google-services.json` for Android — no iOS Firebase config found
- Tooling: ESLint 9 flat config (`eslint.config.js`, on `eslint-config-expo`), Prettier, husky + lint-staged (pre-commit runs ESLint on staged `.ts`/`.tsx`), `eas.json` build profiles, GitHub Actions CI (`.github/workflows/mobile-ci.yml`: typecheck, lint). **There is no test runner or test files at the moment** (Jest was set up and removed again on purpose)

## Folder structure (`src/`)

- Feature-based, not a single `screens/` folder: `src/features/<domain>/*Page.tsx` (a few explicit `*Screen.tsx` live in `components/common/` and `features/onboarding/`)
- `src/features/` domains: `ancillary` (`patient/`, `staff/` splits — home-care nursing/physio), `appointment`, `auth`, `bookings`, `care-ai` (Care AI health-assistant chat, mock replies), `consultation`, `dashboard`, `doctor` (`detail/`, `events/`, `search/`), `events`, `laboratory`, `notification`, `onboarding`, `patient`, `patient-payment`, `patient-qr`, `pharmacy`, `portal`, `profile` (split per role), `radiology`, `referrals`, `settings`, `wallet` — most have their own `components/`
- `src/components/common/` — shared UI, grouped into sub-folders and all re-exported from the barrel `index.ts` (import from `components/common`, not the file path): `layout/` (AppScreenHeader, AppHeader, AppSection, AppFooterBar, AppBottomSheet, AppModal, AppSidebar, SplashScreen…), `buttons/`, `inputs/`, `display/` (AppTypography, AppAvatar, AppIcon…), `feedback/` (StatusModal, ErrorBoundary, OfflineBanner…), `booking/` (booking-flow pieces), `location/`. New shared components go in the matching sub-folder. Design tokens (`APP_COLORS`, `TONES`, `CARD_SHADOW`) live in `src/config/theme.ts`.
- `src/components/layout/` — `SidebarLayout.tsx`
- `src/navigation/` — `AppNavigator.tsx` (root switch: auth vs. authenticated), `AuthNavigator.tsx`, `MainTabNavigator.tsx` (role-conditional tabs), `navigationService.ts`, `routes.ts` (`ROUTES` constants), `types.ts` (param list types), plus the server-driven menu: `NavigationConfigContext.tsx` (fetches the menu), `menuConfig.ts` (types + built-in `DEFAULT_MENU`), `menuIcons.tsx` (icon key -> drawing), `useSidebarMenu.ts` (drawer rows)
- `src/context/` — `AuthContext.tsx` (auth/session/role — **no Redux**, Context + hooks instead), `NetworkContext.tsx`, `ScrollContext.tsx`
- `src/services/` — `apiService.ts` (shared axios instance: auth header, offline short-circuit, session-expiry handling), plus `appointmentService.ts`, `blogService.ts`, `communityService.ts`, `locationService.ts`, `notificationPermissionService.ts`, `qaService.ts`, `reviewService.ts`; some features keep their own local service
- `src/constants/apiUrls.ts` — `BASE_URL` + `API_ENDPOINTS` map (**source of truth for API routes**)
- `src/hooks/useFamilyMembers.ts` (top-level) + feature-scoped hooks
- `src/config/` — `theme.ts` (Paper theme), `toastConfig.tsx`
- `src/types/` — domain type defs + `assets.d.ts`, `react-native-vector-icons.d.ts`
- `src/utils/` — `date.ts`, `formatters.ts`, `jsonUtils.ts`, `networkState.ts`, `s3Utils.ts`, `secureStorage.ts`
- `src/assets/` — images by domain, mirrors `health_care_frontend/src/assets/` structure
- Top-level `assets/` (outside `src/`) — Expo app icons/splash, referenced from `app.json`

## Running / building

```bash
npm start          # expo start
npm run android     # expo run:android
npm run ios         # expo run:ios
npm run web         # expo start --web
```
Other scripts: `npm run typecheck` (`tsc --noEmit`), `npm run lint` (ESLint over `src`; errors fail, the existing warning backlog does not), `npm run format` / `format:check` (Prettier over `src`; some older files are not formatted yet), `prepare` (installs the husky hook). There is no `build` script (builds are `expo run:*` or EAS, see `eas.json`). `metro.config.js` adds `.dcm` (DICOM) as an asset extension and wires `react-native-svg-transformer`. `babel.config.js` uses `babel-preset-expo` + reanimated plugin.

## Navigation

`App.tsx` → `AppNavigator` picks `AuthNavigator` (login → role selection → specialty selection → onboarding → register) or the authenticated `AppStack`, based on `useAuth().accessToken`. Authenticated stack's initial route is `MainTabNavigator` (bottom tabs: Home/Search/Portal-Bookings/Ancillary/Wallet/Profile, tab set varies by `role`), with ~50 additional stack screens reachable per domain (search/doctors, pharmacy, radiology, laboratory, consultation, doctor events, nurse/ancillary staff flows, patient ancillary booking flow, wallet). Route names centralized in `src/navigation/routes.ts`.

**The sidebar and the bottom tab bar are served by the backend** (`GET /api/lookup/navigation`, per role: patient, doctor, ancillary; see `health_care_backend/docs/navigation.md`). The response is only stable `key`s + label + icon key, already ordered, never a route: the app owns what a key does (`useSidebarMenu.ts` for drawer rows, `TAB_TARGETS` in `MainTabNavigator.tsx` for tabs) and silently skips keys it does not know. To add a menu entry: add the row in the backend DB, and map its key here. `DEFAULT_MENU` (mirrors the backend's shipped data) is shown until the first response, when the request fails, for a list the backend sends empty, and for roles with no server menu (pharmacy/radiology/laboratory, which keep the docked tab bar). The menu is refetched whenever the app returns to the foreground.

## Home-care patient no-show

Backend policy: `health_care_backend/CLAUDE.md` ("Home-care (ancillary) patient no-show"); off until the backend sets `ANCILLARY_NO_SHOW_ENABLED`, and every screen below behaves as before while it is off. **Provider** (`features/ancillary/staff/visit/ProviderVisitDetailsPage.tsx`): when `visit.arrival.no_show_enabled`, the footer is "I've arrived" (`markVisitArrived`: the phone's location goes to the server, which checks it is near the address and starts the wait) then, once `wait_ends_at` has passed, "Patient not available" (`reportPatientNotAvailable`, with a confirm) next to "Enter start code"; a reported visit (`NO_SHOW`) can still be started with the patient's code the same day. The wait never starts by itself: `arrival.near_address` is only a hint that shows "You're at the address". **Patient**: a missed visit shows `features/ancillary/components/MissedVisitBanner.tsx` (`AncillaryScheduledDetailsPage`, and `HomeCareVisitView` via `TrackAppointmentPage`'s `missedNotice`): "Tell us what happened" while the patient can still answer, opening the same `features/appointment/components/NoShowReplySheet.tsx` as a doctor no-show (pass `visitId` instead of `appointmentId`; calls `ancillaryNoShowService.ts`), then the outcome in the server's words (recorded as missed / won't count / being reviewed) and the patient's answer, so the choice of reason decides whether it counts; an arrived provider shows "waiting until". The patient is also pushed (FCM): a tap on the push opens the booking (`services/pushNotificationService.ts`, `PATIENT_HOME_CARE_NEWS`), and a tap on the in-app notification does too (`NotificationPage`: `ancillary_scheduled` -> the booking details, `ancillary_booking` / the older `ancillary_order` -> the tracking screen). While booking of every home-care service is paused the two review pages (`AncillaryReviewPayPage`, `AncillaryBookNowReviewPage`) show `BookingRestrictedBanner` and disable Confirm (`useAncillaryBookingRestriction`; the server also answers 403 `BOOKING_RESTRICTED`). The doctor and home-care restriction hooks share `hooks/createBookingRestrictionHook.ts`. The Bookings tab shows a missed home-care order as a past booking with the server's `note` (what happened) and "Tell us what happened" (`isNoShowBooking`: `category === 'ancillary' && missed_visit_id`; the sheet is opened with `visitId`). `TrackAppointmentPage` must never send a `NO_SHOW` order to the "Finding your nurse" screen (`NO_SHOW` is in its `ASSIGNED_STATUSES`; that screen is for an order with no provider yet). `NO_SHOW` is a closed status next to the cancelled ones (`scheduledVisitView.isMissedStatus`, `mapStatusToBookingTab`). Not run on a device yet: no test runner, checked with `npx tsc --noEmit` only. Files here are CRLF, so check Prettier with `npx prettier --check --end-of-line crlf <files>`.

**Patient status strip** (`features/ancillary/patient/HomeCareVisitView.tsx`): the five-step strip is drawn from the server's `timeline` (`visits[].timeline` of the focused visit, else the order's `timeline`; backend `app/ancillary/timeline.py`): the app does not decide the current step, and a missed visit arrives as a `stopped` step (red, "Missed", at the door); a cancelled / expired / failed visit has `outcome` and `outcome_text` instead, the strip is hidden and a banner says it (the order-level "Visit cancelled" banner, or the visit's `outcome_text` while the order goes on). Only a server that sends no `timeline` gets the old status-to-step fallback (`fallbackTimeline`).

**Consultation vitals** (Notes tab of `features/consultation/ConsultationPage.tsx`; design `vitals.html`, variant B: a card that opens a bottom sheet). The first thing in the Notes tab is `components/VitalsNotesCard.tsx`: nothing recorded today shows a dashed "Vitals not recorded" card (last reading, **Record**), otherwise the time, "N need attention" / "All normal", **Edit** and one chip per reading, the most worrying first. Record / Edit open `components/RecordVitalsSheet.tsx` (`AppBottomSheet`, six `components/VitalFieldTile.tsx`: BP systolic / diastolic, pulse, SpO₂, temperature, random sugar; the dot and border of a tile follow the typed value's range). No backend change: today's card is built from the readings of the last 2 days (`GET /api/patients/{id}/vitals?days=2` through `getRecentVitals`, the page's `recentVitals`: each field takes its newest value of the CLINIC day, IST, so a later "others" record without a pulse cannot hide it; the empty card's "Last on 12 Jun" line still comes from `GET .../vitals/latest`) and saved through `recordVitals` in `VitalsService.ts`, one `POST /api/patients/vitals` per vital type with a shared `recorded_at` (`blood_pressure` {systolic, diastolic}, `others` {pulse_rate}, `spo2` {spo2}, `temperature` {temperature}, `glucose_level` {random}); a save returns the records it created and the page puts them into `recentVitals` and `latestVitals` at once (no second request to wait for), so the card and the Overview cards show them immediately. Only new or changed readings are sent (`buildVitalEntries`), so an edit or a retry after a partial failure never repeats a saved one. The logic (fields, ranges, validation, entries, today's summary) is in `vitalsEntry.ts` and the state / save in `useRecordVitals.ts`; `VITAL_THRESHOLDS` now lives in `vitalsEntry.ts` and is shared with the Overview cards. A typed value is refused outside a plausible range (`PLAUSIBLE`: SpO₂ 50-100, temperature 90-110 °F with a hint when it looks like °C, systolic above diastolic) and a clearly LOW reading is flagged like a high one (`CLEARLY_OUT` low values). The draft lives in `RecordVitalsSheet` (a keystroke does not re-render the page; fields not yet touched follow today's readings if they arrive late). Until today's readings are fetched the card says so and `openSheet` waits (`RecentLoad`: a failed fetch shows Retry), so a doctor is never offered an empty sheet for readings already taken. `recordVital` skips the global error dialog; a failed save names the server's reason. The Overview pulse is the most recent of `blood_pressure.pulse` and `others.pulse_rate` (`latestPulse`). With the notes already submitted the card is read-only. Not run on a device yet: `npx tsc --noEmit` only.

**Medical records** (patient; `features/medical-records/`, design `medical record.html`; route `ROUTES.STACK.MEDICAL_RECORDS`). Opened from a sidebar row "Medical records" (HEALTH group, after Treatment History). The backend menu has no such row yet, so the APP adds it (`CLIENT_SIDEBAR_ADDITIONS` / `withClientSidebarRows` in `navigation/menuConfig.ts`, applied in `NavigationConfigContext`; action in `useSidebarMenu`, icon `medical-records` in `menuIcons`): when the row exists in the backend's `navigation_items` / `navigation_entries` tables, delete the addition (a key the server sends is never added twice). `MedicalRecordsPage.tsx`: `AppSearchBar` (the screen shows the signed-in patient's records unless a family member is picked: a row of chips above the search shows whose records: "Me" and each family member (avatar and first name; a tap shows that person's records) and an "Add" chip that opens the booking's `AppFamilyMemberSheet` (pick or add a family member), and every person's list is already fetched, so it switches at once; a record can also be saved to a family member from the upload sheet) with ONE scrolling chip bar under it, like the Find a doctor filter bar: a "Filters" chip first (icon, label and a count when any is on), which opens the same `AppFilterSheet` as Find a doctor (`DoctorFilterSheet` is now a thin wrapper of it) with the records' own categories from `medicalRecordsFilters.ts`: record date and sort order (kind is the chips next to it, who is the family row, so nothing else is filtered); then the kinds as chips (All / Prescriptions / Lab reports / My uploads with counts; the chosen one is filled; the counts follow the filters), `AppDashedActionCard` (Upload), `AppRecordList` (grouped by month; `AppEmptyCard` when empty) and the app's own `AppPhotoSourceSheet` (given `UPLOAD_SOURCE_SHEET`'s texts and an `onChooseFile` row) asks where the file is from and closes itself before the picker opens; the pick (`pickRecordFile`: camera / gallery through `expo-image-picker`, PDF through `utils/pickedFile`) then opens `components/UploadRecordSheet.tsx`, one `AppBottomSheet` with only the details: the file, what it is, the date, and "Saving to" shown by the booking's `AppPatientRow` and changed in the booking's own `AppFamilyMemberSheet`, which also adds a family member on the spot through `useFamilyMembers().addFromDraft` (the details sheet is hidden while it is open, and remounted by a new `key` for every upload); its back arrow goes back to choosing another file). The three generic `App*` components (`AppRecordList`, `AppDashedActionCard`, `AppEmptyCard`) are shared (`components/common`); the logic is pure (`medicalRecordsView.ts`). **On the backend** (`health_care_backend/CLAUDE.md`, "Patient medical records"; `medicalRecordsService.ts`, every call with `skipGlobalError` so the reason shows where the person is looking): `useMedicalRecords` fetches each person's records once, when the family list is ready, with ONE request, `GET /api/patients/records` (`listRecords`, paged 200 at a time; `patient_public_id` only for a family member, the signed-in patient sends none, so the app never needs its own patient id): the backend puts the person's uploads and the prescription of every visit whose notes the doctor submitted in one list (`source` `patient` / `provider` / `visit`; a visit has `appointment_id`, `recordFromApi`), keeps them per person (switching the header is instant, and the "whose record" step shows each person's count) and applies a save or a delete at once, also when a fetch that began earlier ends later (`edits` in the hook). The upload is ONE multipart `POST /api/patients/records` (`kind`, `record_date`, `patient_public_id` for a family member only (the signed-in patient sends none), and one `file` part: a PDF or a photo; one page per record), with `appendFile` from `utils/pickedFile`; the Save button spins, the sheet cannot be closed meanwhile, and on a failure it stays open with the server's reason under the form. A tap on a row fetches fresh signed links (about 5 minutes) through `recordFile`: an upload from `GET /api/patients/records/{id}`, a visit's prescription image from `GET /api/treatments/appointment/{id}/prescription`; a PDF opens in the phone's own viewer (`openWebUrl`), photos and the prescription in `components/RecordViewerModal.tsx` (pinch to zoom on iOS; a "Full size" button opens the photo in the browser, which zooms on every phone). An upload shows under its kind's tab (Prescriptions / Lab reports) as well as My uploads (`tabCounts`, `filterRecords`). `medicalRecordsTypes.ts` mirrors the backend's `RecordOut`; the server's limits are in `recordVisuals.ts` (none left: a record has no title or doctor of its own). A row has no chevron; a record the patient uploaded (`type` `up`) has a small bin at its end (`AppRecordRowData.onDelete`, set by `recordRow`), which asks first and then calls `DELETE /api/patients/records/{id}` (`deleteRecord` skips the global error dialog; a 404 means it is already gone and the row is removed anyway, `isRecordGone`; `removeRecord` in the hook); a record from a doctor, a lab or a visit has none (the server refuses it too, 403). Not done: the lab reports that Karolahealth labs make (the backend has to expose `lab_order_reports` first) and doctors seeing a patient's uploads. Not run on a device yet: `npx tsc --noEmit` only.

## Conventions

- Prettier: tabs, `tabWidth: 4`, no semicolons, single quotes, `printWidth: 120`
- ESLint (`npm run lint`) gates errors; the React-Compiler-era hooks rules (`react-hooks/refs`, `set-state-in-effect`, ...) are warnings because existing code breaks them in bulk. Prettier is configured with `endOfLine: auto`
- Import alias: `@/*` maps to `src/*` (tsconfig `paths`); existing files still use relative imports
- TypeScript strict mode (`expo/tsconfig.base`)
- Screens mostly suffixed `Page.tsx` (not `Screen.tsx`, except a handful of onboarding/common files); services suffixed `Service.ts`; context providers suffixed `Context.tsx` and export a paired `useX` hook
- Route names as string constants in `src/navigation/routes.ts`, not hardcoded in navigators
- `android/` exists on disk despite being gitignored as a "generated" folder — don't assume it's disposable without checking with the user first
- Root-level scratch files (`review.md`, `gemini.md`) are dev notes/leftover compiler output, not maintained docs. `review.md` tracks a phased remediation plan; Phases 1–3 (secure token storage, no plaintext token logging, safe JSON parsing, error boundary, the API URL env fix above, folder/naming standardization) are marked complete and verified against current code as of 2026-09-22. Phase 4/5 items (console-stripping in babel, FlatList conversion, a real Jest suite) are still open — verify against the doc before assuming something in the later phases is done.
